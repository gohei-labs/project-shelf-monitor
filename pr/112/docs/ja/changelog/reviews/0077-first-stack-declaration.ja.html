最初のスタック宣言

このレビューは、プロジェクト最初のコンポーネント宣言 — project-components.json による api コンポーネント（stack backend-python）の宣言、検証済みの最小 FastAPI 骨格 apps/api、そして台帳への scope: stack 導入 — の承認を求めます。スタック導入の最終スキーマステップです。

承認のお願い

  1. api コンポーネントの宣言。project-components.json（新規。開発ルールのコンポーネント契約そのもの）：id api、path apps/api、type backend、stack backend-python、commands.check = uv run ruff check && uv run pytest。契約ゲート（ENV-03）が実マニフェストを検証するようになり、未宣言の実装ディレクトリは CI で失敗します。
  2. 骨格の受け入れ。apps/api：Python 3.12 上の FastAPI（.python-version＋uv.lock で固定）、/health route 1 本、通るテスト 1 本、ruff 設定済み。ファイル操作なし・managed-root アクセスなし（PROJ-01 遵守）。宣言した check コマンドはローカルで緑（CPython 3.12.13、aarch64）。
  3. スタック層の開通。scope: stack をゲートの許可集合に追加（0065 以来の予約値）し、backend-checks・frontend-build を product → stack へ。両者は将来統制のまま（enforcedBy: null）で、product＋stack を表示するようになった Project rules ビューに引き続き並びます。有効化（宣言済み check の CI 配線）は意図的に次のステップに分けています。

リスク

中（ただし正直に限定済み）：宣言は実体を持ちますが、スタックゲートは未配線 — CI で uv run ruff check && uv run pytest を実行するものはまだなく、有効化ステップが着地するまで壊れた api コンポーネントはマージをブロックしません。これはすべての advisory ルールが辿るのと同じ昇格経路です（まず見える形で宣言し、次に強制する）。骨格自体は最小・ローカル検証済みで、ファイル操作面を追加しません。緩和策：ENV-04 の note がこのギャップを明記し、有効化を次のステップとして指名しています。

ここでは決めないこと

  • 有効化：宣言済み commands.check の scripts/check.ps1・CI への配線（CI への uv 導入）、ENV-04 の条件付きゲート化 — 次の PR。
  • web コンポーネント（React / Vite / TypeScript）の宣言 — 同じ型で、ツールチェーン整備後に。
  • Phase 1 の挙動（読み取り専用本棚・managed-root 境界・JSONL ログ — REQ-001..004）— この骨格の上に実装変更として入ります。
  • api の Compose サービス / Dev Container 統合 — 宣言ではなく Phase 1 ランタイム作業の一部。
