Fix the guardrail argument binding

Two wired guardrails have been running on the wrong inputs and reporting success. The secret scanner never saw a pull request body, and the spec-before-implementation gate never saw a real changed-file list. One line of the runner caused both; this change fixes it.

Requested Approval

  1. Fix the runner. Invoke-Guardrail forwarded parameters by splatting an array. PowerShell array splatting binds positionally — a leading "-PullRequestBody" string becomes the first positional value, not a parameter name. It now takes and splats a [hashtable], which binds by name; the type also makes a future array a bind-time error instead of a silent mis-bind.
  2. Accept that two gates start biting. secret-scan will now read PR bodies (a pasted token fails the gate), and spec-before-implementation will now compute changed files from git and demand a change record on implementation pull requests. Both may fail changes that previously passed by accident.

Risk

Low to make, meaningful to absorb. The change itself is three lines in the runner and cannot weaken any gate — no gate loses inputs, two gain the inputs they always declared. The cost lands afterwards: pull requests that would have failed the secret or spec gates have been passing, so the next few pull requests may surface real findings that were previously invisible. That is the intended outcome of repairing a fail-open control, not a regression. Note also what this says about assurance: the suite has been green throughout, because a gate that silently scans nothing still exits 0.

Not Decided Here

  • Whether past merged pull requests should be re-scanned for secrets in their bodies (no token was found in this repository's code; the PR-body path was simply never exercised).
  • Adding a wired regression test for the runner — scripts/tests/ exists but nothing runs it; wiring a test lane is its own change.
  • The component-check activation that uncovered this (it follows in a separate change).
