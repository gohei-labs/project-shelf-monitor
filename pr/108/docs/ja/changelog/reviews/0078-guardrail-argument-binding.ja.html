ガードレール引数束縛の修正

配線済みの 2 つのガードレールが、誤った入力で動作しながら成功を報告していました。秘密情報スキャナはプルリクエスト本文を一度も見ておらず、spec-before-implementation ゲートは本物の変更ファイル一覧を一度も見ていませんでした。原因は実行部の 1 行です。本変更でこれを修正します。

承認のお願い

  1. 実行部の修正。Invoke-Guardrail は配列スプラットでパラメータを転送していました。PowerShell の配列スプラットは位置引数として束縛するため、先頭の "-PullRequestBody" という文字列はパラメータ名ではなく第 1 位置引数の値になります。今後は [hashtable] を受け取ってスプラットし、名前で束縛します。型指定により、将来配列を渡した場合も黙った誤束縛ではなく束縛時エラーになります。
  2. 2 ゲートが効き始めることの受け入れ。secret-scan は PR 本文を読むようになり（貼られたトークンはゲート失敗）、spec-before-implementation は git から変更ファイルを算出し、実装 PR に変更記録を要求します。これまで偶然通っていた変更が今後は失敗しうります。

欠陥の具体

本ホストで、修正前後を実測。

ガードレール実際に受け取っていた値結果
secret-scan（SEC-01）$PullRequestBody = リテラル文字列 -PullRequestBody。本物の本文は破棄PR 本文の ghp_… トークンがゲートを通過（exit 0）。修正後は (PR body):1 :: GitHub token を報告し exit 1。
spec-before-implementation（DR-02）$ChangedFiles = @("-PullRequestBody")。どのコードパスにも一致しない捏造の 1 件一覧毎回「実装コードの変更なし」と結論し、変更記録を要求したことが無かった。修正後は git diff から一覧を算出。

リスク

変更自体は低リスク、受け止めるべき影響は実質的。修正は実行部の 3 行で、どのゲートも弱くなりません——入力を失うゲートは無く、2 つのゲートが宣言どおりの入力を初めて得ます。コストは事後に来ます：これまで secret / spec ゲートで落ちるはずだった PR が通ってきたため、今後数件の PR で、これまで見えなかった本物の指摘が表面化しうります。これは fail-open な統制を修理した結果であり、退行ではありません。あわせて保証（assurance）についての教訓も：ゲートは何もスキャンしなくても exit 0 を返すため、スイートはこの間ずっと緑でした。

ここでは決めないこと

  • 過去のマージ済み PR の本文を秘密情報について再スキャンするかどうか（リポジトリのコードにトークンは無く、PR 本文の経路が一度も動いていなかっただけ）。
  • 実行部の回帰テストの配線——scripts/tests/ は存在するが何も実行していない。テストレーンの配線は別の変更。
  • 本欠陥を発見した契機であるコンポーネントチェックの有効化（別の変更で続く）。
