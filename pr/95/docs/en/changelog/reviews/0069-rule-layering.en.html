Core, stack, and project rule layers

This review asks for approval to adopt the three-layer rule scope model with declaration-based stack activation and Azure-style tracked exceptions.

Requested Approval

  1. Three layers: core (all projects, technology-independent), stack (written once per technology stack, reused), project (thin: declarations + genuinely project-specific rules). Layer derives from the registry's existing scope field. Precedent: NIST baseline / overlay / tailoring.
  2. Activation by declaration: a project adopts a stack's rules by declaring the stack in project-components.json; the conditional gates backend-checks / frontend-build are the registered landing points. Precedent: GitHub reusable workflows and rulesets, ESLint shareable configs, Backstage templates, golden path / paved road.
  3. Exception model: lower layers may only add explicit, tracked exemptions (category Waiver or Mitigated, expiresOn, requestedBy/approvedBy) and can never relax higher-layer rules — the Azure explicit-deny model, with GCP-style child supersession explicitly rejected.

The main risk is designing ahead of use — stack rules and the exemption file schema are intentionally deferred until the first application project exists, so the model may need adjustment on first contact; both deferrals are recorded in the doc and change note.
