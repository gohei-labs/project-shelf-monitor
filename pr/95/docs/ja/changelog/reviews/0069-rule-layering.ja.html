core / stack / project のルール層

このレビューは 3 層のルールスコープモデル（宣言によるスタック有効化と Azure 型の追跡される例外を含む）を採用すること の承認を求めます。

承認をお願いする事項

  1. 3 層：コア（全プロジェクト・技術非依存）、スタック（技術スタック単位で一度書いて再利用）、プロジェクト（薄い層：宣言＋真に固有のルール）。層は台帳の既存 scope フィールドから導出する。前例：NIST の baseline / overlay / tailoring。
  2. 宣言による有効化：プロジェクトは project-components.json でスタックを宣言して、そのスタックのルールを採用する。条件付きゲート backend-checks / frontend-build が受け皿。前例：GitHub reusable workflows・rulesets、ESLint shareable configs、Backstage templates、golden path / paved road。
  3. 例外モデル：下位層は明示的で追跡される exemption（category は Waiver または Mitigated、expiresOn、requestedBy / approvedBy）を追加できるだけで、上位層のルールを緩和できない — Azure の explicit-deny 方式を採用し、GCP 型の子による上書きは明示的に不採用。

リスク

文書のみで、ゲート・スキーマの変更はない。主なリスクは利用に先行した設計であること — スタックルールの実内容と exemption のファイルスキーマは最初のアプリケーションプロジェクトまで意図的に先送りしており、実戦投入時にモデルの調整が必要になり得る。いずれの先送りも文書と変更記録に明記した。

ここでは決めないこと

  • スタック別ルールの実内容（最初のプロジェクトでスタック確定後に書く）。
  • exemption レコードのファイルスキーマ（最初の実例外の際に定める）。
  • controlType の軸分離と guardrails 配列キーの改名（記録済みの先送り。最初のスタック導入のスキーマ変更と同時に実施）。
