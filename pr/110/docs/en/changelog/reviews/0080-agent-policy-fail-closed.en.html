Make the agent permission boundary fail closed

Deleting two keys from agent-policy/policy.json erased the credential-read boundary and the push allowlist. The gate stayed green, the generated config protected nothing, and the PreToolUse hook allowed a push to any remote. Reproduced end to end, then fixed at all three layers.

Requested Approval

  1. Fail closed on a missing key. @($policy.key).Count -eq 0 never fires on a deleted key: PowerShell's @($null).Count is 1. The gate now rejects an absent key, a null, an empty list, and a blank entry (an empty-string prefix matches every remote; a whitespace one matches none — both are meaningless). Applied to credentialDenyRead, pushRemoteAllowedPrefixes, allowBaseline; the structural keys deny / protectedPaths / hooks must exist so no check passes vacuously.
  2. Pin every deny rule the rules name. $requiredDeny held four ids while SEC-01 names curl and wget uploads and GOV-03 names the destructive git commands. It now names all ten. Deleting wget-upload or hard-reset previously passed green.
  3. Check the compiled output, not only the source's self-consistency. The -Verify sync check regenerates the config from the same weakened policy, so it is always "in sync". A new check reads the generated .claude/settings.json and asserts a Read(<path>) deny rule exists for each declared credential path. (This pins that the declared paths reach the config; it does not yet pin that the declared paths are the real credential roots — see Risk.)
  4. Fail closed at runtime and at generation. The PreToolUse hook denies a push to an explicit remote URL when the allowlist is missing/empty/blank; the generator throws instead of compiling the meaningless rules Read() and Read(/**).
  5. Force review on the boundary. agent-policy/ and scripts/hooks/ join the high-risk paths that require a linked review artifact.

Risk

Low to make; the change only adds refusals. It cannot weaken any boundary, and a legitimate policy passes unchanged (verified). What it costs: retiring a deny rule now requires editing the gate — deliberate, matching how scope and guidance values are pinned. What it does not fix: value substitution. A non-blank but overbroad push prefix (["https://"]) passes the gate and the hook then allows every https remote; junk credential paths (["x"]) pass while dropping the real ~/.aws / ~/.ssh / ~/.netrc. Both are now surfaced by the review-artifact gate rather than pinned. $requiredDeny likewise remains hand-maintained, so a new exfiltration channel added to the policy without adding its id here is not pinned. And this repairs one control surface only — the same audit confirmed 26 further fail-opens across the suite, including a secret scanner that misses UTF-16 files.

Not Decided Here

  • Wiring scripts/tests/ into a run lane so these fixes are guarded against regression. Currently nothing runs it.
  • Deriving $requiredDeny from the policy's own categories instead of a hand-maintained list.
