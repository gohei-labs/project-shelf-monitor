API Phase 1 — managed-root 境界の内側の読み取り専用本棚

このレビューは、最初のプロダクトスライス: /status と読み取り専用の /shelf 一覧。全パスが明示的な MANAGED_ROOT 境界を通り、JSONL 運用ログを伴う — REQ-001..004 の API 側 — の承認をお願いするものです。ファイルを変更できるルートは存在しません。

承認していただきたいこと

  1. 読み取り専用の API サーフェスを採用する。GET /status は常に managed-root の設定状態を返す（REQ-003）。GET /shelf?path= はちょうど 1 ディレクトリを一覧する — 名前・種別・ファイルサイズのみで、ファイル内容は決して返さない。未設定 → 503、境界違反 → 403、不存在 → 404、非ディレクトリ → 400。
  2. 境界ポリシーを採用する（REQ-002）。リクエストは POSIX 相対パスのみ。NUL・:・バックスラッシュ・絶対パスは即拒否。実ルートに対して解決するため .. や symlink では脱出できない。resolve_within_root が強制し、symlink 脱出ケースを含む専用テストで担保。
  3. ロギング契約を採用する（REQ-004）。startup / config-loaded / ブロックされたパス試行（security.path/blocked）/ 本棚読み取りを、ルールブックの形式の JSONL で記録 — 名前・件数・設定のみ。「ファイル内容がログに現れない」ことをテストが検証。
  4. モニターのステータス更新を受け入れる。REQ-002/REQ-004/FEAT-004/CONN-002/CONN-003 → implemented。REQ-001/REQ-003/FEAT-001/FEAT-002 → active（Web 側が残るため）。FEAT-003 と web コンポーネントは planned のまま。

リスク

リスクの中心は、オーナーの実ファイルシステム上のパス処理。緩和策: 境界レイヤーがファイルシステムへの唯一の入口で、トラバーサルと symlink 脱出に対してユニットテスト済み。ブロックされた試行はログに残り可視化される。サーフェス全体が読み取り専用で、将来の書き込み機能には File Operation Gate（dry-run・確認・ログ）の要求が先に立つ。プライバシー: ログと応答は名前と件数のみでファイル内容を含まず、テストがそれを強制。ページネーションは未実装で、巨大ディレクトリは大きな応答を返す（オーナー専用の確認画面であり Phase 1 では許容）。

ここでは決めないこと

  • Web UI（apps/web）とそのスタック宣言 — REQ-001/REQ-003 を完全に「implemented」にする画面。
  • FEAT-003: API からの最近ログイベントの読み出し。
  • 大きなディレクトリのページネーション・フィルタリング。
  • 実運用での MANAGED_ROOT の Dev Container / Compose への配線 — 現状はマシンごとの `.env` の関心事。
