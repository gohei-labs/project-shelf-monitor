Rename the registry rule array key

This review asks for approval to rename the registry's rule array key from guardrails to rules and bump the registry schemaVersion to 2 — the first, purely mechanical step of the stack-onboarding schema work.

Requested Approval

  1. Rename the key. monitor/registry.json keys its 37 entries as rules, matching the settled vocabulary (PR #94: not every rule is an enforced guardrail). Entry content is byte-identical; the guardrails pillar name is unrelated and unchanged.
  2. Version the schema. schemaVersion moves 1 → 2, and every consumer (check-registry.ps1, the monitor generator, guardrail-lib.ps1) requires version 2 — a stale consumer fails loudly instead of silently iterating a missing key and treating the registry as empty.
  3. Start the onboarding sequence. This consumes deferral 2 of 2 in layering.md's Deferred Schema Work, whose landing point is the first stack onboarding — started by the owner's stack decision of 2026-07-10 (FastAPI / Python backend, React / Vite / TypeScript frontend). The controlType axis split and scope: stack follow as separate small changes.

Risk

Low. Mechanical rename with a version guard — no rule, gate wiring, or monitor content changes, verified by identical regenerated pages and a green full suite. The residual hazard of any key rename is a missed consumer reading the old key; the schemaVersion bump converts that failure mode from silent (empty rule list) to loud (explicit version error), and the only three consumers in the repository are updated in this same change.
