API Phase 1 — read-only shelf behind a managed-root boundary

This review asks for approval of the first product slice: /status and a read-only /shelf listing, every path passing an explicit MANAGED_ROOT boundary, with JSONL operational logs — the API side of REQ-001..004. No route can modify a file.

Requested Approval

  1. Adopt the read-only API surface. GET /status always answers with the managed-root configuration (REQ-003); GET /shelf?path= lists exactly one directory — names, kinds, file sizes; never file contents. Unconfigured → 503, boundary violation → 403, missing → 404, non-directory → 400.
  2. Adopt the boundary policy (REQ-002). Requests are POSIX-relative only; NUL, :, backslash, and absolute paths are rejected outright; resolution happens against the real root so .. and symlinks cannot escape. Enforced by resolve_within_root and covered by dedicated tests including a symlink-escape case.
  3. Adopt the logging contract (REQ-004). JSONL records in the rule-book shape for startup, config-loaded, blocked path attempts (security.path/blocked), and shelf reads — names/counts/configuration only. A test asserts file contents never appear in the log.
  4. Accept the monitor status flips. REQ-002/REQ-004/FEAT-004/CONN-002/CONN-003 → implemented; REQ-001/REQ-003/FEAT-001/FEAT-002 → active (their web half is still planned). FEAT-003 and the web component stay planned.

Risk

The risk center is path handling on the owner's real filesystem. Mitigations: the boundary layer is the only filesystem entry point, it is unit-tested against traversal and symlink escape, blocked attempts are logged and visible, and the whole surface is read-only — the File Operation Gate's dry-run/confirmation demands stay ahead of any future write feature. Privacy: logs and responses carry names and counts, never contents; one test enforces exactly that. Listing has no pagination yet; a huge directory returns a large response (inspection screen, owner-only, acceptable for Phase 1).

Not Decided Here

  • The web UI (apps/web) and its stack activation — the screen that makes REQ-001/REQ-003 fully "implemented".
  • FEAT-003: reading recent log events back through the API.
  • Pagination or filtering of large directories.
  • How MANAGED_ROOT is wired in Dev Container / Compose for real use — currently a per-machine `.env` concern.
