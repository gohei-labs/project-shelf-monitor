Split controlType into behavior and guidance

This review asks for approval to replace the registry's blended controlType field with two orthogonal fields — behavior (the mechanism) and guidance (the adoption obligation), per the AWS Control Tower precedent. Registry schemaVersion moves to 3. The mapping is 1:1; no rule changes meaning and no gate changes wiring.

Requested Approval

  1. Two axes instead of one. behavior ∈ hard-gate / conditional-gate / external-control / none; guidance ∈ mandatory / planned. The former working-agreement = none + mandatory; future-control = none + planned. All 37 rules map 1:1 (24 / 1 / 1 / 6 / 5); the enforced/unenforced split is unchanged.
  2. Gate the axes. check-registry.ps1 validates both fields as closed sets, moves the status-consistency rules to behavior (advisory ↔ none), rejects guidance: planned on any wired or external behavior, and fails on a leftover controlType. recommended / elective stay rejected until a stack rule first needs them — the same deliberate-edit principle as scope: stack.
  3. Monitor presentation. Cards chip the behavior; a second "Planned" chip marks future controls. The detail pane lists both axes ("Behavior" / "Guidance"). Unenforced cards now read "No wired gate" instead of a pseudo-mechanism word.

Risk

Low-to-medium. The data mapping is mechanical and 1:1, verified by unchanged enforced/unenforced counts and a green full suite. The real change surface is presentation and vocabulary: the owner-facing monitor replaces "Working agreement" / "Future control" chips with "No wired gate" (+ "Planned"), so the two retired words now live in the group heading and the docs rather than on each card. If that reads worse in practice, relabeling is a generator-only change — the data model stays orthogonal either way.

Not Decided Here

  • Introducing scope: stack, re-scoping backend-checks / frontend-build, and the component declaration — the remaining onboarding step, its own review.
  • Adopting recommended / elective guidance values — reserved; arrives with the first stack rule that needs them.
  • Any change to the status field vocabulary (active / advisory / conditional / external) — it stays as-is; only its consistency target moved from controlType to behavior.
