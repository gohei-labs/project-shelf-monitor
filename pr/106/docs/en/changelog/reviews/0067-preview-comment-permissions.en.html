Preview comment must reach the pull request

This review asks for approval to grant the Monitor Preview workflow the pull-request write permission it needs to post the preview link, and to make a failed comment fail the step instead of hiding as a warning.

Requested Approval

  1. Raise the Monitor Preview workflow token from pull-requests: read to pull-requests: write. Commenting on a pull request via the issues API requires this; issues: write alone is not enough, which is why every recent PR was missing its preview-link comment (403, swallowed).
  2. Treat the preview-link comment as an owner-facing control: if creating or updating the comment fails, the step now prints the preview URL to the log and fails, so the regression can never be silent again.
  3. Remove the unused issues: write grant from the same permissions block. The workflow's only issues-API calls target a pull request, which the pull-requests permission governs — proven by the 403 that occurred while issues: write was present (owner principle: delete what is unnecessary).

What Changed

One workflow file, plus the paired change note 0058.

Changed fileWhat changed
.github/workflows/monitor-preview.ymlPermissions: pull-requests: read → write, and the unused issues: write removed (with a comment explaining both). The comment step's catch no longer downgrades failure to a warning; it logs the preview URL and exits 1.

Risk

The token gains write access to pull requests in this repository only, and it runs in the trusted workflow_run context from the default branch — PR-modified code never sees it (unchanged design). The stricter failure mode means a future permission cap will break the step loudly; the documented fallback is the MONITOR_PREVIEW_COMMENT_TOKEN secret.

Not Decided Here

  • Whether to set the MONITOR_PREVIEW_COMMENT_TOKEN secret; the default token now suffices.
  • Backfilling preview comments on already-open PRs (PR #89's links were added to its body by hand).
  • Any change to what the preview publishes or where it publishes.
