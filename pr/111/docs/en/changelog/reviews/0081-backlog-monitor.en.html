A pre-Issue backlog with a browser monitor

This review asks for approval of a backlog: a browser-visible staging area for candidate work items, generated from a tracked source on the existing Pages/mirror pipeline — the place to record something surfaced during work and decide, together, whether it becomes a GitHub Issue.

Requested Approval

  1. Adopt the backlog. Source monitor/backlog.json → generated monitor/backlog.html / .ja.html, deployed through the existing Pages site and public mirror. It operationalizes the no-unilateral-issues agreement: the owner decides what graduates to an Issue.
  2. Adopt the type vocabulary (research-grounded). Deep research into GitHub Issue Types, Azure DevOps, Google Issue Tracker, Mozilla BMO, and Conventional Commits found one rule: type, severity, area, status, and tags are separate axes. The type set is bug / feature / enhancement / refactor / docs / task / question — GitHub-default-aligned and Conventional-Commits-mappable. A fail-open is type: bug with a fail-open/cwe-636 tag, not a type; security is a tag, mirroring how the rule registry keeps domain: security separate from a rule's mechanism.
  3. Seed it with the audit. The 27 confirmed fail-open findings become the first items, plus one surfaced by this review (28 total: 2 accepted, addressed in PR #110; 26 candidate). Nothing is filed as an Issue yet — that is the next, owner-led step.
  4. Gate it. check-backlog.ps1 (registry GOV-06) validates the source and keeps the monitor in sync — so a candidate cannot be shown with an out-of-set type/impact/status and the page cannot drift from the source.

Risk

Low. This adds a monitoring surface and a validating gate; it changes no enforcement of existing rules. The gate was built with this session's lesson applied — required keys are checked by presence (not @($x).Count, which is 1 on a deleted key), and every enumerated field is a closed set — and eight negative tests confirm it fails closed. The judgment risk is elsewhere: the backlog is triage material, and the Issue-graduation criteria are a rubric, not a gate. Over-filing Issues and losing a real defect in chat are both failures the backlog is meant to make visible, but the owner's call still decides each item.

Not Decided Here

  • Which of the 26 candidates become GitHub Issues, and in what priority — the next, owner-led triage pass over this board.
  • Whether the machine-translated Japanese item text needs a human pass — the English is primary; a translate-then-verify pass produced the Japanese.
  • An importer for future items — they are hand-added to monitor/backlog.json for now.
