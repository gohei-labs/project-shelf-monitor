Issue 化前のバックログとブラウザモニター

このレビューは、バックログ — 候補作業項目の、ブラウザで見える一時置き場。追跡ソースから既存の Pages/ミラーパイプラインで生成 — の承認を求めます。作業中に湧いたものを記録し、一緒に眺めて、GitHub Issue にするかを決める場所です。

承認のお願い

  1. バックログの採用。ソース monitor/backlog.json → 生成 monitor/backlog.html / .ja.html。既存の Pages サイトと公開ミラーで配信。申し合わせ no-unilateral-issues を運用可能にする：何を Issue に昇格させるかはオーナーが決める。
  2. type 語彙の採用（調査に基づく）。GitHub Issue Types・Azure DevOps・Google Issue Tracker・Mozilla BMO・Conventional Commits の deep research で、一貫した規則が判明：type・severity・area・status・tags は別々の軸。type 集合は bug / feature / enhancement / refactor / docs / task / question — GitHub デフォルト整合・Conventional Commits 写像可能。fail-open は type: bug に fail-open/cwe-636 タグで、type ではない。security も tag で、ルールレジストリが domain: security をルールの仕組みと分けているのと同じ。
  3. 監査で初期投入。確定した 27 件の fail-open 所見が最初の 27 項目になる（2 件 accepted、PR #110 が対応。25 件 candidate）。まだ何も Issue にはしていない — それが次の、オーナー主導のステップ。
  4. ゲートで守る。check-backlog.ps1（レジストリ GOV-06）がソースを検証しモニターを同期させる — 集合外の type/impact/status を持つ候補は表示できず、ページはソースからドリフトできない。

低。監視面と検証ゲートを追加するもので、既存ルールの強制は変えない。ゲートは今セッションの教訓を適用して作った — 必須キーは presence で判定（削除キーで 1 になる @($x).Count ではなく）、列挙フィールドはすべて閉集合 — 8 つの負のテストが fail-closed を確認済み。判断のリスクは別のところにある：バックログは仕分け材料であり、Issue 昇格基準はゲートではなくルーブリック。Issue の過剰登録も、実在する欠陥を chat で失うことも、バックログが可視化すべき失敗だが、各項目はオーナーの判断が決める。
