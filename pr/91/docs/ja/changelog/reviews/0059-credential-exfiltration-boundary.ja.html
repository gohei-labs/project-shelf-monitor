シークレットの「読んで持ち出す」経路を塞ぐ

この資料は、エージェントが既存の認証情報を読み、外部へ送信する経路（read-then-exfiltrate）を、読み取り側と送信側の両方からハーネスで塞ぐことの承認を求めます。

承認のお願い（Requested Approval）

  1. 読み取り側の遮断。credentialDenyRead の各パス（~/.aws/credentials・~/.ssh 等）を Read ツールの deny ルールに生成し、さらに PreToolUse ガードが、これらのパスを参照する Bash/PowerShell コマンド（cat・grep・Windows パス表記含む）を位置を問わず deny します。
  2. 送信側の遮断。外部送信チャネルをポリシー deny に追加: gist 共有（gh gist とトークンラッパー経由）、リクエストボディ送信（curl -d/--data*/-F/-T・wget --post-*/--body-*、--フラグ=値 形式含む）。プレビュー検証等の素の GET は許可のまま。
  3. 未知リモートへの push の遮断。pushRemoteAllowedPrefixes（現在は gohei-labs 配下のみ）外のリモート URL への git push を PreToolUse ガードで deny します。名前付きリモート（origin）は許可のまま。
  4. ゲート化と可視化。必須 deny に gh-gist-share・curl-upload を追加し、credentialDenyRead / pushRemoteAllowedPrefixes が空になったら fail。レジストリに credential-exfiltration-boundary（secrets カテゴリ・hard-gate）を登録し、コミット時スキャンが拾えない脅威として文書化します。

リスク（Risk）

正当な作業の過剰ブロック。リクエストボディ付き curl/wget は一律 deny のため、将来 API へ正当に POST したい場合もブロックされます。その時はポリシーを編集（ask ゲート付き）して意図的に許可する運用です。認証情報パスの参照 deny も同様に、パス文字列に言及するだけのコマンドを塞ぐ可能性がありますが、安全側の誤りです。

残余経路。許可済み GET のクエリ文字列への埋め込み、WebFetch ツール経由の送信、TLS 内のペイロードはテキスト照合では塞げません。これらは OS レベルの egress 制御（#62）の領分として文書化し、隠しません。

照合の限界。コマンド照合はテキストベースで、難読化（変数展開・base64 等）には勝てません。最終防壁はサンドボックス（#62）です。

決めないこと（Not Decided Here）

  • OS レベルの egress 制御・サンドボックス（Issue #62 — 次の PR）。
  • WebFetch / WebSearch のドメイン制御。
  • 難読化されたコマンドの解析（解決後コマンドの検査）。
  • 環境変数経由のシークレット参照制御。
