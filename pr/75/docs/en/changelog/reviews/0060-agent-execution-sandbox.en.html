Agent execution sandbox (default-deny egress, no credential mounts)

This review asks for approval to place the final barrier below the harness, at the OS: harden the devcontainer with default-deny outbound networking and keep credentials out of it entirely.

Requested Approval

  1. Default-deny egress firewall. .devcontainer/init-firewall.sh applies an iptables policy at container start. Only loopback, DNS, established connections, and ports 80/443 to resolved IPs of the policy egressAllowlist (currently five domains: GitHub plus the public monitor) are allowed. The allowlist source of truth is the same agent-policy/policy.json the harness configs compile from. Because the kernel enforces it, the boundary holds even if prompt injection bypasses the model's judgment.
  2. Make no-credential-mounts an invariant. The workspace bind-mounts only the repository. If a change ever mounts ~/.ssh, ~/.aws, or similar into compose, the config gate fails — inside the sandbox there is nothing credential-shaped to read in the first place.
  3. Register as an external control with a config gate. As Issue #62 specifies, agent-execution-sandbox is registered as an external-control, and check-sandbox-config.ps1 (a hard config check) continuously verifies the firewall exists and is wired, NET_ADMIN is granted, the allowlist stays narrow (bare lowercase hostnames only), and no credential mount appears.

Risk

IP rotation. Domains resolve to IPv4 addresses at apply time, so if GitHub rotates IPs, connections to an allowlisted domain fail until the (idempotent) script is re-run. There is no TLS inspection, which is exactly why the gate enforces allowlist narrowness.

Coverage. The firewall protects devcontainer runs (local/CI), not a native Windows session — there the harness layers from #64/#63 are the enforcement. This asymmetry is documented explicitly.

Explicit fail-open. Without NET_ADMIN or iptables the firewall warns and continues (so unprivileged environments keep working). Presence and wiring are protected by the hard config gate; actual application is visible in the start-up log.

Not Decided Here

  • Whether to also adopt Claude Code's built-in Bash sandbox (opt-in, Bash-only).
  • A runtime CI test that verifies the firewall actually applied.
  • Domain controls for WebFetch / WebSearch.
  • Extending OS-level controls beyond the devcontainer (native Windows).
