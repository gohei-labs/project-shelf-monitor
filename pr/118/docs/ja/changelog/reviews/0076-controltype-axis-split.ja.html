controlType を behavior と guidance に分離

このレビューは、台帳の混在フィールド controlType を、直交する 2 フィールド — behavior（仕組み）と guidance（適用義務）— に置き換えることの承認を求めます。AWS Control Tower の前例に従い、registry の schemaVersion は 3 に。マッピングは 1:1 で、ルールの意味もゲート配線も変わりません。

承認のお願い

  1. 1 軸から 2 軸へ。behavior ∈ hard-gate / conditional-gate / external-control / none、guidance ∈ mandatory / planned。旧 working-agreement = none + mandatory、旧 future-control = none + planned。全 37 ルールが 1:1 で対応（24 / 1 / 1 / 6 / 5）。強制／非強制の区分は不変です。
  2. 軸をゲートで守る。check-registry.ps1 は両フィールドを閉じた許可集合で検証し、status 整合規則を behavior に移し（advisory ↔ none）、配線済み・外部 behavior への guidance: planned を拒否し、残存 controlType を失敗させます。recommended / elective はスタックルールが最初に必要とするまで拒否 — scope: stack と同じ「意図的な編集を強制する」原則です。
  3. モニターの表示。カードのチップは behavior を表示し、将来統制には「予定」の第 2 チップが付きます。詳細ペインは両軸（「挙動」/「適用義務」）を表示。非強制カードは疑似的な仕組み語の代わりに「ゲート未配線」と読めます。

リスク

低〜中。データのマッピングは機械的な 1:1 で、強制／非強制の件数不変と全チェック緑で確認済み。実質的な変化面は表示と語彙です：オーナーが見るモニターのチップが「作業合意」「将来統制」から「ゲート未配線」（＋「予定」）に変わり、退役した 2 語はカード上ではなくグループ見出しと文書に残ります。実運用で読みにくければ、ラベル変更は生成器のみの修正で済みます — データモデルの直交性はどちらでも保たれます。

ここでは決めないこと

  • scope: stack の導入、backend-checks / frontend-build の再スコープ、コンポーネント宣言——残る導入ステップ。別途レビューします。
  • recommended / elective の採用——予約済み。必要とする最初のスタックルールと同時に導入します。
  • status フィールドの語彙（active / advisory / conditional / external）の変更——現状維持。整合の相手が controlType から behavior に移っただけです。
