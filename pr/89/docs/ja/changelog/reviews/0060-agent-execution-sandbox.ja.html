エージェント実行サンドボックス（既定 deny の egress・認証情報非マウント）

この資料は、ハーネスの下の OS レベルに最後の防壁を置く — devcontainer を強化し、外向き通信を既定 deny にし、認証情報を持ち込まないことの承認を求めます。

承認のお願い（Requested Approval）

  1. 既定 deny の egress ファイアウォール。.devcontainer/init-firewall.sh がコンテナ起動時に iptables を適用します。許可はループバック・DNS・確立済み接続・ポリシー egressAllowlist（現在5ドメイン: GitHub 系と公開モニターのみ）の解決 IP への 80/443 だけ。allowlist の正本はハーネス設定と同じ agent-policy/policy.json です。プロンプトインジェクションがモデルの判断を回避しても、カーネルが強制するため境界が保たれます。
  2. 認証情報の非マウントを不変条件にする。ワークスペースはリポジトリのみを bind mount します。~/.ssh・~/.aws 等をマウントする変更が compose に入ったら設定ゲートが fail します（サンドボックス内には読むべき認証情報がそもそも無い状態を保つ）。
  3. 外部制御としてのレジストリ登録＋設定ゲート。Issue #62 の指定どおり agent-execution-sandbox を external-control として登録し、check-sandbox-config.ps1（hard な設定検証）がファイアウォールの存在・配線・NET_ADMIN・allowlist の狭さ（素の小文字ホスト名のみ）・認証情報マウント不在を常時検証します。

リスク（Risk）

IP ローテーション。ドメインは適用時に IPv4 へ解決されるため、GitHub 等が IP を変えると許可済みドメインへの接続が失敗します。復旧はスクリプト再実行（冪等）です。TLS 検査はしないため、allowlist の狭さをゲートで強制します。

適用範囲。ファイアウォールが守るのは devcontainer 実行（ローカル/CI）で、Windows ネイティブセッションは対象外 — そこでは #64/#63 のハーネス層が強制を担います。この非対称は文書に明記しました。

fail-open の明示。NET_ADMIN や iptables が無い環境ではファイアウォールは警告して続行します（非特権環境を壊さないため）。存在・配線は hard な設定ゲートが守り、実際の適用は起動ログの警告で可視化されます。

決めないこと（Not Decided Here）

  • Claude Code 内蔵の Bash サンドボックス（opt-in・Bash限定）の採用可否。
  • ファイアウォール適用の実挙動を CI で検証するランタイムテスト。
  • WebFetch / WebSearch のドメイン制御。
  • devcontainer 以外（Windows ネイティブ）への OS レベル制御の拡張。
