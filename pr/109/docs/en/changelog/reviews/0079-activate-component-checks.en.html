Activate the declared component checks

This review asks for approval to make a declared commands.check actually run as a gate: a new conditional gate executes each backend component's check in its own directory, CI installs uv so it bites, and backend-checks graduates from future control to conditional gate.

Requested Approval

  1. Run the declared check. New gate check-component-checks.ps1, wired into scripts/check.ps1, runs uv run ruff check && uv run pytest inside apps/api. A failing lint or test now blocks a merge. CI installs uv so the gate runs there instead of skipping.
  2. Promote ENV-04. backend-checks: advisory / future-control / planned → conditional / conditional-gate / mandatory, with a real enforcedBy. frontend-build stays a future control (no frontend component declared); its note now names the two steps that flip it.
  3. Adopt the runner contract. Written into the development rules: cwd = the component path; PowerShell 7 executes the command string (so && chains); one registry rule owns one component type (via -ComponentType) so a rule cannot silently enforce a type it does not claim; a missing leading program is a visible skip, a program missing later in a chain is a failure.
  4. Clean up retired vocabulary. Delete the unused $validControlType / $controlLabels maps and stale CSS left in the application-monitor scripts (the dead code the #106 review flagged; owner approved).

Risk

Medium. This gate executes command text read from a tracked file — that is the point of the component contract, and the protections are that project-components.json is review-gated like any control file and the component path is confined to the repository. A first draft of the gate parsed the command by splitting on && / ; to collect program names; that mistook sys.exit(3) inside a quoted python -c argument for a missing program and silently skipped the check while reporting success — a fail-open. A negative test caught it before commit; the gate now inspects only the leading token and fails closed when a later program is missing. Two further fail-open paths were found in review and closed here: a component retyped in the contract alone (backend → worker) would silently leave the gate's scope — the architecture record and the contract must now agree on type; and the component path's containment check was lexical, so a committed symlink (on the path or an ancestor) could place the working directory outside the repository — the gate now canonicalizes through links and rejects an outside target. Residual: the Dev Container / Bash lane has no uv, so it skips (visibly) and under-enforces relative to the PowerShell CI lane.

Not Decided Here

  • Declaring the web component and flipping frontend-build — same two steps, its own change.
  • Adding uv (and later Node) to the Dev Container so the Bash lane enforces the same gate.
  • The httpx → httpx2 migration for the Starlette TestClient deprecation — owner-approved for the next dependency change.
  • Phase 1 behavior (read-only shelf, managed-root boundary, JSONL logs) — implementation changes on the skeleton this gate now protects.

Terminology Check

Does this artifact use industry-standard terms, mapping any project-specific wording to standard vocabulary?

Term in this artifactStandard term / meaning
Conditional gateA control that runs only when its precondition holds (here: the toolchain exists); the registry's behavior: conditional-gate, analogous to a CI job with an if: condition.
Fail-open / fail-closedOn an unknown or degraded condition, a fail-open control lets the change through (unsafe); a fail-closed control blocks or errors (safe). The parsing bug described above was fail-open.
Visible skipA control that cannot run reports that fact in its output and counts, rather than being reported as a pass — so "green" never means "silently ran nothing".
Graduation (advisory → enforced)The policy-as-code pattern of adopting a rule in audit/advisory mode first, then promoting it to a blocking gate (Azure Policy audit → deny; Kyverno Audit → Enforce).
