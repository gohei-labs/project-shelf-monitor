宣言済みコンポーネントチェックの有効化

このレビューは、宣言された commands.check を実際にゲートとして実行することの承認を求めます：新しい条件付きゲートが各 backend コンポーネントの check をそのディレクトリで実行し、CI は uv を導入して実効化し、backend-checks は将来統制から条件付きゲートへ昇格します。

承認のお願い

  1. 宣言した check を実行する。新ゲート check-component-checks.ps1 を scripts/check.ps1 に配線し、apps/api 内で uv run ruff check && uv run pytest を実行します。lint やテストの失敗はマージをブロックします。CI は uv を導入するため、スキップせずゲートが走ります。
  2. ENV-04 の昇格。backend-checks：advisory / future-control / planned → conditional / conditional-gate / mandatory。実体のある enforcedBy を付与。frontend-build は将来統制のまま（frontend コンポーネント未宣言）で、note に切り替えの 2 ステップを明記。
  3. 実行契約の採用。開発ルールに明文化：cwd = component の path。コマンド文字列は PowerShell 7 が実行（&& は連鎖）。1 台帳ルールが 1 component type を担当（-ComponentType）し、担当と宣言していない type を黙って強制しない。先頭プログラムの欠落は可視のスキップ、連鎖後続のプログラム欠落は失敗。
  4. 廃止語彙の整理。application-monitor スクリプトに残っていた未使用の $validControlType / $controlLabels と古い CSS を削除（#106 レビューが指摘した死にコード。オーナー承認済み）。

リスク

中。本ゲートは追跡ファイルから読んだコマンドテキストを実行します——それがコンポーネント契約の目的であり、保護は project-components.json が他の制御ファイルと同様にレビューゲートを通ること、および component path がリポジトリ内に閉じ込められることです。ゲートの初版はプログラム名を集めるためコマンドを && / ; で分割していましたが、これは python -c の引用符内の sys.exit(3) を「存在しないプログラム」と誤認し、成功を報告しながら check を黙ってスキップしていました（fail-open）。コミット前に負のテストが捕捉し、現在は先頭トークンのみを見て、後続プログラム欠落では fail-closed に倒れます。残余：Dev Container / Bash レーンには uv が無いため（可視の）スキップとなり、PowerShell の CI レーンより強制が弱いままです。

ここでは決めないこと

  • web コンポーネントの宣言と frontend-build の切り替え——同じ 2 ステップ。別の変更で。
  • Dev Container への uv（将来は Node）の追加。Bash レーンでも同じゲートを効かせるため。
  • Starlette TestClient 非推奨に対する httpx → httpx2 移行——次回の依存変更でオーナー承認済み。
  • Phase 1 の挙動（読み取り専用本棚・managed-root 境界・JSONL ログ）——本ゲートが守るようになった骨格の上の実装変更。
