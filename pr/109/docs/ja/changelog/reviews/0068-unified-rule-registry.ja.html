オーナーレビュー0068提案2026-07-09

ルール台帳は一つ、ガードレールは強制ゲートのみ

このレビューは 3 つのルール台帳を monitor/registry.json に一本化し、「ガードレール」という語を配線済みゲートが変更をブロックできるルールに限定すること の承認を求めます。

承認をお願いする事項

  1. 単一台帳：すべてのルールは monitor/registry.json の 1 エントリで、明示的な domain（security / process-quality）を持つ。「domain なし＝process」の暗黙既定は廃止し、registry ゲートが強制する。前例：NIST SP 800-53 Rev.5 は別台帳を単一カタログに統合し、区別を control family として保持した。
  2. LLM-GR-001〜008 の識別子体系を廃止する。各項目は台帳エントリとして存続（LLM-GR-003 は artifact-purpose-separation として登録。「提案中」は既存語彙 advisory＋working-agreement で表現）。改稿した台帳文書に旧 id→台帳 id の恒久的な対応表を置く。履歴は書き換えない。
  3. 語の規律：「ガードレール」＝配線済みのブロックゲートを持つルール（hard-gate / conditional-gate）。AWS Well-Architected の階層化（control＝要求、guardrail＝その技術的実装）に従い、AWS Control Tower が guardrails を controls に改名した文書化済みの理由（「業界の用法との整合のため」）を踏まえる。強制されないルールは working agreement とし、development.md は「開発ルール」に改題。

リスク

分類と文書のみの変更で、ゲート挙動は変わらない。主なリスクは過去記録との表記のずれ：旧記録には LLM-GR id と旧表題が残るが、恒久的な対応表で読み替える。registry ゲートは今後 domain を欠くエントリを失敗させるため、暗黙既定へのサイレントな回帰は起こらない。

ここでは決めないこと

  • controlType の behavior / guidance 直交軸への分離（AWS Control Tower の前例）— 既知の改善点として記録し、Issue #93 に委ねる。
  • core / stack / project の層構造と例外（exemption / waiver）モデル — Issue #93。
  • 一時停止中ルール LLM-GR-006 の表現修正 — Issue #90。
