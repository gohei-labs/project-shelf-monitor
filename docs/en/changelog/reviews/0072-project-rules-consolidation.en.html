Consolidate project rules and define the classification test

This review asks for approval to write down the criterion "general development rules are core; product-specific rules are Project rules", and unify the rule source of truth into the single registry.

Requested Approval

  1. Adopt the classification test. layering.md now states the three-question test: (1) portability — copy the rule text into the next, unrelated project; if it still makes sense, it is core. (2) If it fails only because of a technology stack, it is stack layer. (3) Otherwise it is project (scope: product). Litmus: a proper noun in the rule text (product name, path, phase number, requirement ID) means project.
  2. Unify the source of truth. The second rule location (developmentRules in application-monitor.json) is retired; all rules live in the registry, and the gate fails if developmentRules reappears. Of the five placeholders, three die as duplicates of core gates, two are rewritten with their substance kept (PROJ-01/PROJ-04), and two requirement-derived rules (boundary, logging) are registered as future-controls (PROJ-02/PROJ-03).
  3. Remove the "Development rules" page. The page and nav item that showed placeholders for a non-existent application are retired; the project layer's browser surface is the Project rules view (10 entries). This also resolves the name collision with the core development rules doc.
