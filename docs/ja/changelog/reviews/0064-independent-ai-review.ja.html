独立コンテキストによる AI レビューを強制する

この資料は、「コードを書いた本人が自分でレビューして良しとする」自己レビューを、監査記録のレベルで不可能にすることの承認を求めます。品質ゲート3部作の第2弾（#81）です。

承認のお願い（Requested Approval）

  1. 独立性の要求を記録形式に組み込む。AI Review Record の同一セクション内に Author context:（変更を書いたコンテキストの識別子）と Reviewer context:（レビュー専用コンテキストの識別子）の両方を宣言し、両者が異なることをゲートで強制します。鮮度チェック（head 一致）を通過した記録に対して検査するため、「古い記録の独立性だけ借りる」ことはできません。
  2. 正直な位置づけを承認する。宣言された識別子は構造化された表明（attestation）であり、暗号学的な証明ではありません。ただし違反には監査記録への明示的な虚偽記載が必要になり、それは永続的に可視化されます — 「うっかり自己レビュー」は構造的に不可能になります。
  3. 実運用の実績に基づく形式化。この形式は PR #84 で実地に使われたものです: 実装セッションとは別の新規コンテキストのエージェントが4パスの攻撃的レビューを行い、P1×2 を含む11指摘を検出、全修正がテスト化されました。今回の PR 自体も、また別の新規レビュアーによる独立レビューを受けています。

リスク（Risk）

表明ベースの限界。悪意あるエージェントが偽の Reviewer context を書くことは技術的には可能です。この統制の価値は「事故と怠慢の排除」（うっかり・なし崩しの自己レビューを構造的に防ぐ）と「違反の可視化」（偽装には監査記録への明示的な虚偽記載が必要）にあります。暗号学的な同一性証明はこのリポジトリの規模では過剰と判断し、正直に限界を文書化します。

運用コストの増加。すべての実装 PR に独立レビューの実施が必須になります（#84 実績で1パス2〜6分程度）。品質ゲート3部作の本旨であり、意図されたコストです。

決めないこと（Not Decided Here）

  • 必読文書の決定的強制 — 第3弾 #80。
  • レビュアー識別子の技術的検証（セッション ID の突合等）。
  • レビューの質・深さの自動評価。
