レジストリのルール配列キー改名

このレビューは、registry のルール配列キーを guardrails から rules に改名し、registry の schemaVersion を 2 に上げることの承認を求めます——スタック導入スキーマ作業の、最初の純粋に機械的な一歩です。

承認のお願い

  1. キーの改名。monitor/registry.json は 37 エントリを rules キーで保持し、確定済みの語彙（PR #94：すべてのルールが強制ガードレールではない）と一致させます。エントリ内容はバイト同一。pillar 名の guardrails は無関係で無変更です。
  2. スキーマのバージョン化。schemaVersion を 1 → 2 に上げ、すべての消費側（check-registry.ps1・モニター生成・guardrail-lib.ps1）がバージョン 2 を要求します——古い消費側は、存在しないキーを黙って走査してレジストリを空扱いする代わりに、明示的に失敗します。
  3. 導入連鎖の開始。これは layering.md「先送りしたスキーマ作業」2 件のうち 1 件の消化です。着地点である最初のスタック導入は、オーナーのスタック決定（2026-07-10：バックエンド FastAPI / Python、フロントエンド React / Vite / TypeScript）で開始しました。controlType の軸分離と scope: stack は、別の小さな変更として続きます。

リスク

低。バージョンガード付きの機械的改名——ルール・ゲート配線・モニター内容の変更はなく、再生成ページの同一性と全チェック緑で確認済み。キー改名一般の残余リスクは旧キーを読む消費側の見落としですが、schemaVersion の引き上げがその故障モードを「静か（空のルール一覧）」から「明示的（バージョンエラー）」に変換します。リポジトリ内の消費側は 3 スクリプトのみで、すべて本変更で同時に更新済みです。

ここでは決めないこと

  • controlType の behavior / guidance 軸分離——導入連鎖の次項目。別途レビューします。
  • scope: stack の導入、backend-checks / frontend-build の再スコープ、コンポーネント宣言（project-components.json）——最初のコンポーネント骨格と同時に着地します。
  • スタック選定そのもの（FastAPI / Python + React / Vite / TypeScript）は、アーキテクチャ記録に記録済みのオーナー決定です。本アーティファクトは導入の起点として引用するのみです。
